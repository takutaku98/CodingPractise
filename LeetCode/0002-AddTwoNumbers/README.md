# 2. Add Two Numbers

## 問題

2 つの非負整数が、**桁を逆順に並べた**単方向リストで与えられる(1 ノード = 1 桁)。
2 数の和を、同じ形式のリストで返す。

- 例: `l1 = [2, 4, 3]`(= 342)、`l2 = [5, 6, 4]`(= 465)→ 答えは `[7, 0, 8]`(= 807)

逆順であることがミソで、**リストの先頭 = 一の位**。つまり先頭から順に足していけば、筆算とまったく同じ「下の桁から足して繰り上げる」処理になる。

## 解法: 筆算シミュレーション + ダミーヘッド

### 核心となる発想

筆算でやっていることをそのまま書く。各桁で必要なのは 3 つの足し算だけ:

> その桁の和 = `l1 の桁 + l2 の桁 + 前の桁からの繰り上がり(carry)`

- その桁に書く数字は `sum % 10`
- 次の桁に持ち越す繰り上がりは `sum / 10`(0 か 1 にしかならない)

### ループの継続条件は「‖(または)」

```csharp
while (l1 != null || l2 != null || carry != 0)
```

3 つの条件のどれか 1 つでも残っていれば続ける:

1. `l1 != null` — l1 にまだ桁が残っている
2. `l2 != null` — l2 にまだ桁が残っている(`342 + 65` のように**長さは揃っていない**)
3. `carry != 0` — 最後の桁で繰り上がった(`5 + 5 = [0, 1]` の 2 ノード目はこれで生まれる)

短い方のリストが先に尽きたら、その桁は `l1?.val ?? 0` で 0 として扱う(null 条件演算子 `?.` と null 合体演算子 `??` の組み合わせ)。

### ダミーヘッド(番兵)パターン

「結果リストの先頭ノードだけ特別扱いになる」問題を消す定石。

```csharp
var dummy = new ListNode(); // 中身は使わない捨てノード
var tail = dummy;           // 答えの末尾を指し続けるポインタ
// ... ループ内: tail.next = new ListNode(...); tail = tail.next;
return dummy.next!;         // 本当の先頭は dummy の次
```

`tail.next` に新ノードを繋いだら **`tail = tail.next` で末尾を進める**。これを忘れると、毎回同じ場所(`tail.next`)を上書きするだけで、リストが伸びない。

### 具体例のトレース

`l1 = [2, 4, 3]` (342)、`l2 = [5, 6, 4]` (465) の場合:

| 桁 | l1 | l2 | carry(入) | sum | 書く数字 (sum % 10) | carry(出) (sum / 10) |
|----|----|----|-----------|-----|--------------------|----------------------|
| 一の位 | 2 | 5 | 0 | 7 | 7 | 0 |
| 十の位 | 4 | 6 | 0 | 10 | 0 | 1 |
| 百の位 | 3 | 4 | 1 | 8 | 8 | 0 |

→ `[7, 0, 8]` = 807 = 342 + 465 ✓

## 最初の実装で手が止まった原因

書きかけのコードには惜しいポイントが 4 つあった:

1. **carry を計算したのに使っていない**。`digit = sum / 10` まで出せていたのに、それを**次の桁の足し算に加える**線が繋がっていなかった。carry はループの外で 1 回作る変数ではなく、**ループを跨いで運ばれる状態**。
2. **`l5.next` を毎回上書きしていて、リストが伸びない**。`l5.next = new ListNode(...)` の後に `l5 = l5.next` がないので、ループが何周しても結果は 2 ノードのまま。
3. **ループ条件が `&&`**。`l3.next != null && l4.next != null` だと短い方が尽きた時点で止まってしまい、`342 + 65` のような長さ違いや、最後の繰り上がり(`5 + 5 = [0, 1]`)を処理できない。
4. **return がない**(コンパイルエラー)。あと `remider2` のタイポも。ちなみに「余り」は英語で **remainder**(reminder は「リマインダー・思い出させるもの」)。

また、`l1` を `l3` にコピーして始めていたが、これは不要。C# の変数はノードへの**参照**なので、`l1 = l1.next` と進めても呼び出し元のリスト自体は壊れない(ノードの `val` や `next` に代入しない限り安全)。

## 計算量

- 時間: O(max(m, n)) — 長い方のリストを 1 回走査するだけ
- 空間: O(max(m, n)) — 答えのリスト分(それ以外は carry など定数個)

### Theory(具体例 5 件)

| l1 | l2 | 期待値 | 確認したいこと |
|----|----|--------|----------------|
| `[2, 4, 3]` | `[5, 6, 4]` | `[7, 0, 8]` | 基本形(342 + 465 = 807) |
| `[0]` | `[0]` | `[0]` | ゼロ同士 |
| `[9,9,9,9,9,9,9]` | `[9,9,9,9]` | `[8,9,9,9,0,0,0,1]` | 長さ違い + 繰り上がりの連鎖 + 桁数が増えるケース |
| `[5]` | `[5]` | `[0, 1]` | 最後の繰り上がりだけでノードが 1 個増えるケース |
| `[1, 8]` | `[0]` | `[1, 8]` | 片方が実質 0 |

### プロパティベーステスト(FsCheck)

ランダムな桁の並び 2 つからリストを作って足し、「リストを数値(BigInteger)に戻したとき、ちゃんと 2 数の和になっているか」を検証する。リスト操作の実装と、数値としての足し算という**別の経路**で同じ答えを計算して突き合わせるのがポイント。桁数の上限がない(int や long に収まらない長さでも正しい)ことも、BigInteger 経由なら自然に確認できる。
